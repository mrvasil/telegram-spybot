## Главное

`telega-manager` — небольшой временный кэш входящих сообщений, который пересылает сохранённое после удаления. Для задачи «сохранить каждое полученное от Telegram поле и каждый доступный файл» уже написанное ядро `spybot` сильнее. Полезные идеи ZIP: сохранение вложения из контекста ответа, понятное уведомление о подключении и естественная повторная отправка разных типов медиа. Копировать его модель хранения и политику удаления не следует.

## Что ZIP теряет и что нельзя перенимать

1. **Практически все исходные поля.** `build_content` оставляет короткий вручную выбранный словарь (`handlers.py:109–123`): entities, caption_entities, reply/forward-контекст, media_group_id, flags, структурированные сообщения и будущие поля пропадают. `extract_media` выбирает только один тип и последнее фото (`83–101`), не сохраняет миниатюры и остальные размеры. Текущий `collect_media` обходит каждый `file_id`, сохраняет JSON path и метаданные, а версии хранят исходный словарь. Не заменять это whitelist-обработчиком ZIP.
2. **Замена медиа при редактировании.** Правка записывает только `build_content`; если оригинал уже есть, новое вложение вообще не скачивается (`handlers.py:208–218`). В `storage.py:145–153` один `media_path` на сообщение, а не на версию. Текущая связь media → version принципиальна: копии до и после правки должны оставаться независимыми.
3. **Потерянный факт неизвестного удаления.** Нет записи — обработчик молча пропускает ID (`handlers.py:240–249`). Нужен текущий tombstone: удаление неизвестного сообщения сохраняется, поздний оригинал не отменяет факт удаления.
4. **Неполная история и смешение идентичностей.** Ссылка HMAC содержит только `chat_id:message_id`, без `business_connection_id` (`crypto.py:66–69`). У таблицы нет update ID и event identity (`storage.py:24–40`); каждое повторное edit добавляет revision, upsert способен заменить оригинал (`134–171`). Сохранить текущие составные ключи и idempotency по update ID.
5. **Исходящие и их данные пропускаются.** Проверка `_is_owner` отбрасывает собственные сообщения и собственные edits (`handlers.py:192–218`), кроме отдельного reply-hook. При новом требовании полного архива поступившие от Telegram исходящие тоже важны; нельзя наследовать этот фильтр. Старый пункт плана об исходящих как отдельной опции следует сверить с последним требованием пользователя.
6. **Reply-hook не создаёт архивную копию.** `handle_owner_reply` только скачивает и отправляет байты, не вызывает Store (`handlers.py:221–237`). Сбой отправки/потеря DM не должен уничтожать единственную полученную копию. Текущие contextual-версии устраняют этот недостаток.
7. **Неподтверждённое обещание view-once/TTL.** README обещает «how you keep view-once media» (`README.md:13–14`), текст `/start` — «works for view-once / TTL media» (`handlers.py:348–349`). Код делает обычный `get_file`/download и сообщает неуспех (`126–139,225–233`). Обхода или восстановления не предоставленного Telegram содержимого здесь нет. Корректно: сохранить доступные поля и полученные байты; при отсутствии `file_id`/доступа — честная причина недоступности. Скрытый отправитель пересылки тоже не восстанавливается: сохраняется только доступный `forward_origin`, имя и флаги.
8. **Автоматическое уничтожение архива.** По умолчанию текст живёт 30 дней, файлы 7 дней, затем вытесняются при 1 ГБ (`config.py:38–41`, `storage.py:201–225`). Для задачи сохранения навсегда это неподходящие defaults. В текущем `Settings.retention_days=0`; удаление должно оставаться явным выбором владельца. Недостаток диска должен давать состояние/тревогу, а не скрытое FIFO-стирание.
9. **Нет надёжного outbox и media retry.** `download_media` ловит ошибку и возвращает `None` без повторной задачи (`handlers.py:126–139`); удаление сразу отправляется в сеть (`240–253`). `_retry` после трёх `RetryAfter` возвращает `None` вместо ошибки (`18–31`), поэтому вызывающая сторона может принять неотправленное за выполненное. Текущие durable jobs, leases и uncertain notification state важнее простого retry-loop.
10. **Риск потребления памяти и блокировки приёма.** Файл полностью загружается в bytearray, затем bytes и ещё шифруется целиком (`handlers.py:136`, `storage.py:145–148`); синхронные SQLite/файловые операции выполняются из async handler. Размер реально скачанных байтов отдельно не ограничивается. Сохранить потоковую текущую загрузку с пределом, checksum, временным файлом, fsync и атомарным commit.
11. **Уведомление может не вместиться.** Всё удалённое сообщение и все правки собираются одним `send_message` без разбиения (`handlers.py:263–280`). Текущий длинный архив нельзя ограничивать лимитом одной Telegram-карточки; разбиение относится только к отображению.

## Небольшие шаги с наибольшей пользой сейчас

1. **Приоритет скачивания до потери доступа.** ZIP подтверждает ценность немедленного получения файла, но не предлагает надёжного планировщика. Сейчас `_claim_jobs` выбирает `ORDER BY id`, а обход `collect_media` перечисляет в том числе миниатюры и маленькие размеры фото. Добавить приоритет/старение медиа-задач: сначала доступные первичные вложения и контекст недавно полученного сообщения с TTL-метаданными, затем вспомогательные размеры/миниатюры; никогда не отбрасывать последние. Не блокировать intake ожиданием скачивания. Проверка: большой хвост thumbnail-задач не задерживает новый первичный файл; старые задачи не голодают.
2. **Закрепить сценарий контекстного восстановления.** В текущих тестах есть вложенные snapshots и media, но явно проверить ответ владельца на ранее не полученный файл, последующее удаление целевого ID и рестарт между принятием update и загрузкой. Это сохраняет полезный сценарий ZIP без его потерь. Внешний/неполный reply с file_id, но без полного chat/message identity, должен сохраняться как исходный контекст с файлами, без выдуманной идентичности.
3. **Добавить уведомления о смене подключения через outbox**, не связывая их с сохранением updates и не сообщая содержимое чужих чатов.
4. **После capture-проверок добавить естественный просмотр media**, оставив выдачу оригинальных байтов документом и текущие ограничения защищённого содержимого.

Задачи 1–3 имеют небольшой объём и дают проверяемый эффект. Идеи 1 и дополнительная проверка 2 — вывод сравнения с новой целью, а не реализованные функции архивного проекта. Для них нужны точечные синтетические тесты; ZIP и реальные Telegram-аккаунты запускать не требуется.
